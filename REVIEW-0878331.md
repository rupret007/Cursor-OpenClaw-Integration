## Findings

### HIGH — The prompt-injection fence is not connected to the live lookup/tool boundary

Locations: `first-officer/guard/sanitize.py:40-46`,
`services/andrea_sync/andrea_router.py:828-838`,
`services/andrea_sync/server.py:3915-3936`,
`services/andrea_sync/server.py:3978-4006`,
`scripts/andrea_sync_openclaw_hybrid.py:383-399`

`visible_to_tools()` is only a predicate; no production caller uses it.
`restricted_fetch.py` likewise has no production caller. Live news, grounded
research, and recent-message lookup instead launch the normal OpenClaw agent.
That agent prompt explicitly encourages using available skills, including
messaging, and `route_reason` is only prompt text—not a route-specific tool
allowlist. The new fence therefore does not establish that fetched pages or
tool results cannot invoke an outbound-capable skill.

Recalled memory has a narrower issue: fenced notes are inserted into a
`system` message as ordinary text. The fence markers are not interpreted by a
parser or enforced by the model transport. The direct LiteLLM reply path does
not itself expose tools, so I did not find a direct memory-to-external-send
call path, but the claim that fencing makes the note non-instructional is not
enforced.

Repro:

1. Search for `visible_to_tools` and `restricted_fetch`; production use is
   absent outside their definitions, tests, and documentation.
2. Trace `_fetch_live_news_summary` or `_maybe_grounded_research_reply` through
   `_run_direct_openclaw_lookup` to `_create_openclaw_job`.
3. Inspect the generated OpenClaw prompt: lookup routes receive the same
   skill-first agent interface as other routes, with no denylist or capability
   token.

This invalidates `INSTALL.md:160-162` and the corresponding safety claim in
`STATUS.md:141`. A route-level tool policy, plus an adversarial integration
test proving that page/tool text cannot invoke messaging, is required.

### HIGH — Outbound approval is not bound to an exact, verified delivery

Locations: `services/andrea_sync/server.py:2948-2997`,
`services/andrea_sync/server.py:4012-4040`,
`services/andrea_sync/server.py:4234-4240`,
`services/andrea_sync/server.py:4336-4345`,
`scripts/andrea_sync_openclaw_hybrid.py:630-649`

The pending draft stores target, body, capability, and timestamps, but no
approval nonce/digest, origin channel, or origin message identity. Drafts are
keyed by principal when one exists, so an exact confirmation phrase in
another task for that principal can consume the same draft.

More importantly, confirmation launches a general agent and treats its
model-produced `ok` status as delivery proof. There is no structured receipt
bound to the approved target and exact body. Any `ok` result clears the draft
and reports `outbound_message_sent`, even if no messaging adapter ran or a
different action occurred.

Offline repro performed: replace `_create_openclaw_job` with a stub returning
`{"ok": true, "user_summary": "Synthetic success claim."}`, invoke
`_send_pending_outbound_message`, and record whether the draft is cleared.
The method returned `outbound_message_sent` and cleared the draft without a
delivery call.

Bind approval to a digest over action, target, exact body, principal, origin,
and expiry. Require a non-model, tool-generated delivery receipt matching that
digest before clearing the draft or reporting success.

### HIGH — A Playwright report with a fatal report-level error can pass green

Locations: `first-officer/qa/flaky.py:91-119`,
`first-officer/qa/flaky.py:171-215`

`produce()` validates only `suites`. It ignores Playwright's top-level
`errors` collection and does not bind the output to expected projects or test
counts. One clean test is enough for `evaluate()` to return `ok: true` even
when the report also records a fatal collection/global error.

Offline repro performed: construct a report with one first-attempt passing
test and a nonempty top-level `errors` array, then call `produce()` and
`evaluate()`. The result was `report_level_error_gate_ok True`.

Active, expired, and orphaned quarantine entries themselves remain red as
claimed. The bypass is incomplete report ingestion, which can make the same
gate green without quarantine doing so. Reject any report-level error and
bind evaluation to the expected project/test inventory.

### MEDIUM — Activation publishes before validating the approved digest or creating rollback

Locations: `first-officer/release.py:70-88`,
`first-officer/release.py:158-173`,
`first-officer/install.py:164-193`,
`INSTALL.md:208-230`,
`JEFF-ACTIONS.md:9-18`

The activation plan runs `sha256sum --check`, which verifies files against the
archive's own manifest, but does not compare the manifest digest with the
operator-approved release digest. It then moves the candidate into the
release store. The exact manifest-to-release check occurs later in
`install.prepare()`, after publication.

A self-consistent archive with the wrong manifest, an unusable backup parent,
or a prepare-time validation failure therefore leaves a read-only release
directory published under the approved name with no usable rollback
directory. A later legitimate attempt at that digest is refused because the
directory already exists. The gateway has not switched at that point, but the
operation is not atomic and the printed rollback instruction can name a
backup that was never created.

Repro: run the activation dry-run and inspect the order. The only pre-publish
checksum command is `sha256sum --check`; publication precedes
`install.py prepare`. This also differs from `INSTALL.md:215`, which documents
an explicit manifest-digest comparison as part of the sequence.

The config and verifier pin are restored byte-for-byte by the tested rollback
when the live state still exactly matches the candidate. The rollback does not
remove the published candidate or undo separately provisioned reader/proxy
state, so “one rollback” is accurate only for the config, pin, and service
restart—not for the combined release.

The build plan also uses `tar -cf` at `first-officer/release.py:53` without
refusing an existing archive, so a prior artifact at that path can be
overwritten without backup.

### MEDIUM — The hash chain accepts complete truncation

Locations: `first-officer/acceptance/cycle.py:93-123`,
`first-officer/acceptance/cycle.py:334-382`,
`INSTALL.md:120-130`

Every verification starts from an in-process genesis value; there is no
external head, keyed MAC, signed checkpoint, or required minimum sequence.
If the audit log is truncated to empty while no saved fact remains,
`verify()` returns success. An existing routine receipt is also ignored when
there are no retained routine rows.

Offline repro performed: run one routine, truncate only `audit.log`, leave its
receipt in place, and call `verify()`. It returned
`truncated_audit_verified_lines 0`.

The chain detects edits and middle-line deletion while a trusted prefix
remains, but it does not support the documented “missing line is a failure”
claim against whole-log deletion. Persist and verify an authenticated head or
checkpoint, and reject orphan receipts/pending state.

### MEDIUM — LiteLLM policy rendering accepts unsafe pricing

Location: `first-officer/litellm/configure.py:72-89`

The renderer rejects only the special case where both configured token prices
equal zero. It accepts negative, non-finite, nonnumeric, or partially missing
prices and emits a supposedly fail-closed budget configuration. The
acceptance fixture covers positive prices only.

Offline repro performed: supply a routed primary with a negative input price,
a fallback with positive prices, and a valid lane/fallback plan.
`candidate_config()` accepted it (`negative_model_price_accepted True`).

Require finite numeric prices greater than or equal to zero and require at
least one positive charge dimension for every routed deployment before
rendering.

### MEDIUM — “Private HTTPS” LiteLLM endpoints are not enforced

Locations: `first-officer/litellm/configure.py:102-114`,
`services/andrea_sync/litellm_api.py:21-40`,
`services/andrea_sync/litellm_api.py:56-70`,
`INSTALL.md:50-57`

Plain HTTP is correctly restricted to loopback, but any HTTPS hostname is
accepted. The management path then sends the proxy master credential, and the
runtime path sends the lane credential and prompt data. Nothing verifies that
the endpoint is the reviewed private service or even resolves privately.

The operator documentation calls this a private proxy URL, but the code does
not enforce that property. Require a reviewed host allowlist or pinned
endpoint identity; otherwise a typo or malicious configuration can disclose
credentials and prompts to an unrelated HTTPS service.

### MEDIUM — The secret/PII scan silently ignores directory symlinks and named trees

Locations: `first-officer/privacy/scan.py:21-27`,
`first-officer/privacy/scan.py:150-161`,
`first-officer/privacy/scan.py:270-284`,
`INSTALL.md:150-158`

File symlinks fail, but `os.walk()` places a symlink to a directory in
`names`; the scanner neither follows nor reports it. Trees named `data` or
`artifacts` are also skipped everywhere, including default log discovery.
That is weaker than the documentation's claim to scan the checkout and any
log under it.

Offline repro performed: create a checkout containing only a directory
symlink to a benign external directory and call `scan_files()`. It returned
zero findings and zero files (`directory_symlink_findings_files 0 0`).

Reject directory symlinks explicitly. Limit named-tree exclusions to
documented, verified paths, or scan their logs/sensitive text separately.
