## Step 3: Hatchet lane queue and the Restate fallback

`first-officer/lanes/queue.py` queues one review lane on Hatchet and calls Restate only when Hatchet definitely did not accept it. The Hatchet call is the documented stable trigger, `POST /api/v1/stable/tenants/{tenant}/workflow-runs/trigger`, and the run id is `run.metadata.id`. The Restate call is the documented send ingress, `POST /restate/send/{service}/{handler}`, with an `idempotency-key`. A connection refusal or HTTP 425 or 429 is a definite refusal. A timeout, HTTP 408, any 5xx, a dropped connection, a redirect, an authentication failure, or any other answer is unknown: the lane stays off Restate because Hatchet may already have it and the two backends do not share an idempotency check. The private append-only ledger records that unknown row and a later attempt sends nothing until an operator has looked. A definite refusal from both backends is retryable. The same lane, head and pull request are not sent twice, including when two dispatchers race. Tokens stay in the environment, HTTP is loopback-only, a public address is refused, and environment proxies are ignored so a credential cannot follow a redirect or a proxy.
